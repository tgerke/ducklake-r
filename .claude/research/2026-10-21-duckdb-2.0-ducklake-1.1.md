# DuckDB 2.0 and DuckLake 1.1: what ducklake-r should change

Researched 2026-10-21, the day both shipped. Sources are the release posts
(duckdb.org "Announcing DuckDB 2.0.0", ducklake.select "What's New in
DuckLake 1.1"), the DuckDB 2.0 and DuckLake 1.1 docs (cloned from
duckdb/duckdb-web and duckdb/ducklake-web, with a diff of DuckLake's
`docs/1.0` against `docs/stable`), the duckdb-r NEWS at the v2.0.0 tag, the
DuckLake extension source, and probes run on this machine. Both releases are
newer than the model's training data, so none of this comes from memory.

Builds tested, on macOS arm64:

- duckdb R package 2.0.0, built from the `v2.0.0` tag of duckdb/duckdb-r
  into a scratch library (engine v2.0.0, source id `d54cbbe3df`), DuckLake
  extension `417a9117f5`.
- duckdb R package 1.5.5 from the default library, for comparison.

Not tested: PostgreSQL and MySQL catalogs, Windows, a DuckLake catalog
served over Quack, encrypted lakes with deletion vectors, and the icu
extension with a non-UTC session time zone.

## Recommendation

Make this the pre-1.0.0 pass and require duckdb 2.0.0.

The package already runs on 2.0. Against a fresh 1.1 catalog the suite gets
1,244 expectations passing and 7 failing (all 1,257 pass on 1.5.5; the gap
is expectations that never ran after an error), and the 7 failures come
from two upstream changes covered below. The case for moving the floor is
what 1.1 makes possible: partition keys, sort keys, and table options in
`CREATE TABLE`, options set inside the transaction that creates the table,
nested schemas, and comments on view columns. All of these need the 2.0
extension. Keeping 1.5 support would put a version branch in every rewrite
path, for an LTS line that DuckDB supports until March 2027 and that users
who need it can stay on with ducklake 0.9.0.

## The upgrade hazard: DuckDB-file catalogs

When DuckDB 2.0 writes to a lake whose catalog is a DuckDB file, it rewrites
that file at storage version 69, which no 1.5 client can open. DuckLake's
upgrade page says so ("any write from a newer DuckDB release can make the
file unreadable by older DuckDB clients"), and the probes confirm it: a 1.0
catalog made on 1.5.5 and then written by 2.0 (one `INSERT`, no migration,
format still 1.0) fails on 1.5.5 with

```
cannot initialize database with storage version 7 - which is lower than
what the database itself uses (69). The storage version of an existing
database cannot be lowered.
```

There is no option that avoids it. `DUCKLAKE_VERSION '1.0'` pins the catalog
format, not the file's storage version, and a lake created that way on 2.0
is also unreadable on 1.5.5. Forwarding `META_STORAGE_VERSION 'v1.5.0'`
fails with `Unexpected duplicate option "storage_version"`, because DuckLake
sets the option itself. A writable attach from 2.0 that only read data left
the file readable on 1.5.5.

A SQLite catalog does not have the problem: a 1.0 lake made on 1.5.5,
written by 2.0 (an inlined row and a Parquet file), still read correctly on
1.5.5. PostgreSQL should behave the same way but was not tested.

So for a team sharing one DuckDB-file catalog, the first person who upgrades
the duckdb R package and writes to the lake locks everyone on 1.5.x out of
it. NEWS, `vignette("deployment")`, and the `attach_ducklake()` docs should
say this plainly: move every client of a DuckDB-file catalog to 2.0 at the
same time, take a `backup_ducklake()` first, and use SQLite or PostgreSQL
when clients cannot upgrade together.

Catalog format migration is a separate, opt-in step. `AUTOMATIC_MIGRATION`
moves a 1.0 catalog to 1.1 and cannot be undone (asking for 1.0 afterwards
fails with "Cannot downgrade a DuckLake catalog"). After that no 1.5 client
can use the lake, whatever the backend.

## What the 2.0 and 1.1 releases add, and where each lands

### Behavior changes that break or alter current calls

- Time travel to a future timestamp is refused. "Cannot time travel to
  a future timestamp" comes back from `AT (TIMESTAMP => ...)` and from the
  change-feed functions. Six of the seven failures are tests that ask for
  `snapshot_time + 1` or `Sys.time() + 5`. `get_ducklake_table_asof()` with
  `Sys.time()` still works, because the time is in the past by the time the
  query runs. Through dbplyr the error arrives wrapped in "Can't query
  fields", so `get_ducklake_table_asof()`, `get_table_changes()` with
  timestamp bounds, `restore_table_version(timestamp = )`, and
  `attach_ducklake(snapshot_time = )` should check the time in R and abort
  with a clear message.
- An untyped `NULL` gets the `"NULL"` type. duckdb-r 2.0 notes that
  `CREATE TABLE ... AS` now makes a `"NULL"`-typed column from `SELECT
  NULL`, and dbplyr renders `mutate(flag = NA)` as `NULL`. On a 1.1 catalog,
  `create_table()` and `replace_table()` from such a pipeline store a
  `"NULL"` column (R reads it back as integer `NA`); before 2.0 it was
  `INTEGER`. On a 1.0 catalog the same call fails with "DuckLake 1.0 does
  not support the NULL type". DuckLake added the type for exactly this case
  and `set_column_type()` can promote it later, so I would document it
  (with `NA_character_` and friends for a typed placeholder) rather than
  intervene.
- `auto_compact = false` now also skips a table named explicitly in
  `flush_inlined_data()`, `merge_adjacent_files()`, and
  `rewrite_data_files()`, and orphan cleanup follows only the lake-wide
  setting. The maintenance docs and the options table in `R/options.R`
  describe the old rule.
- Compaction results are one row per operation, and `files_created`
  can be more than 1, or 0. `merge_adjacent_files()` and
  `rewrite_data_files()` report `nrow(result)` as the number of output
  files (`R/maintenance.R:207`, `:461`); they should sum `files_created`.

### Works on 1.0 and 1.1 catalogs under DuckDB 2.0

- Layout and options in `CREATE TABLE`: `PARTITIONED BY`, `SORTED BY`,
  and `WITH (...)`, also for `CREATE TABLE ... AS`, as one snapshot inside
  a transaction (probe: one snapshot, partition and sort rows written,
  options stored). `SORTED BY` in `CREATE TABLE` takes ascending keys only;
  `DESC` or a null order still needs `ALTER TABLE ... SET SORTED BY` on the
  empty table. This suggests `partition_by`, `sort_by`, and `options`
  arguments for `create_table()`: today a table created and then
  partitioned keeps its first load unpartitioned.
- `ALTER TABLE ... SET (...)` and `ALTER TABLE ... RESET (...)` for
  table options. `RESET` is new: today the package has no way to remove a
  table override. Configuration changes are not snapshot-versioned.
- `merge_adjacent_files(newer_than, older_than)` (probe: accepted) and
  `rewrite_data_files(max_compacted_files)` (probe: accepted). The
  package exposes neither yet.
- `skip_stats_columns`, a new table-only option, and the
  `ducklake_target_file_size` session setting.
- Broader `add_data_files()` imports: `FLOAT16` into `FLOAT`,
  `TIMESTAMPTZ_NS`, `TIME_NS`, `TIMETZ`, top-level `VARIANT`, native Parquet
  `GEOMETRY`; Hive partition values; `NOT NULL` enforced on import. Docs
  only.
- Faster catalog operations and better file pruning, with nothing to do.

### Needs a 1.1 catalog

- Nested schemas (`CREATE SCHEMA lake.sales.europe`), with DuckLake's
  own error on a 1.0 catalog ("DuckLake 1.0 does not support nested
  schemas"). The design question is below.
- Comments on view columns (above).
- Epoch partition transforms `epoch_year`, `epoch_month`, `epoch_day`,
  and `epoch_hour`. `set_table_partitioning()` rejects them today
  (`R/partitioning.R:63`); `partition_expressions()` already round-trips
  them. The docs should also say why they matter: `month(ts)` alone gives
  January 2020 and January 2021 the same partition value.
- The `"NULL"` type and its promotion.
- `VARIANT` inlining on PostgreSQL and SQLite catalogs.
- Exact string statistics and row-group counts in the catalog
  (`row_group_count` on `ducklake_data_file` and `ducklake_delete_file`).
  `list_ducklake_files()` or `plot_table_files()` could show the count;
  low priority.
- Multi-snapshot Puffin delete files for the experimental
  `write_deletion_vectors` option. The encryption docs need one line: Puffin
  deletion-vector files are written unencrypted even on an `ENCRYPTED`
  lake.
- The `_ducklake_` prefix is reserved for column names.

### Catalog version handling

New lakes are created at 1.1 and existing 1.0 lakes stay at 1.0 unless
attached with `AUTOMATIC_MIGRATION` (both confirmed). `attach_ducklake()`
needs:

- A `ducklake_version` argument for `DUCKLAKE_VERSION`, so a team that still
  has 1.5 clients on a SQLite or PostgreSQL catalog can create a 1.0 lake.
- Rewritten `automatic_migration` docs (`R/attach_ducklake.R:75`). They
  describe the 0.4 to 1.0 upgrade; the option now moves 1.0 to 1.1, and the
  docs should say it is permanent and needs every client on 2.0.
- The `metadata_schema` docs say the default is `main`; DuckLake now
  documents the backend default (`main` for DuckDB and SQLite, usually
  `public` for PostgreSQL).

`get_ducklake_info()` should report the catalog format version, so a user
can see whether a lake has been migrated. A `migrate_ducklake()` that takes a
`backup_ducklake()` first and then re-attaches with `AUTOMATIC_MIGRATION`
would encode DuckLake's own advice (back up first, check every client); it
is optional.

### DuckDB 2.0 and duckdb-r changes

- Lambda syntax: the package sends no single-arrow lambdas. Nothing to
  change.
- The PEG parser is the default. The suite and its snapshot tests
  passed, so no error text the tests match on changed.
- dbplyr: duckdb-r's dbplyr backend has needed dbplyr 2.6.0 since
  duckdb-r 1.5.6 and warns with an older one. DESCRIPTION still says
  `dbplyr (>= 2.5.0)`.
- `duckdb_error` conditions carry `error_type` and `raw_message` (since
  1.5.6). The places that match error text with `grepl()` could match on
  the type instead; optional.
- Integer `//` and `%` by zero now raise an error instead of returning
  `NULL`. Not the package's concern, but users' dbplyr code can hit it.
- Windows (`windows_amd64_mingw`, v2.0.0): `ducklake`, `sqlite_scanner`,
  `httpfs`, `quack`, `icu`, `json`, and `parquet` exist; `postgres_scanner`,
  `mysql_scanner`, `aws`, and `azure` still do not.

### Quack

Quack is stable in 2.0 and no longer documented as a beta.

- The 1.5.3 gate (`check_quack_version()`, `R/quack.R:293`) goes with a 2.0
  floor, and any experimental wording in the Quack article can go.
- `quack_serve()` gained `secret`, `create_secret_if_not_exists`,
  `ssl_cert_file`, and `ssl_key_file`, and non-local servers serve HTTPS by
  default. Clients gained `SSL_FINGERPRINT`, `CLIENT_ID`, and
  `HEARTBEAT_TIMEOUT`. New functions: `quack_server_list()`,
  `quack_active_connections()`, `quack_generate_keys()`, `quack_cancel()`.
- `ATTACH` followed by the new `CONNECT` statement is now the recommended
  way to route a session to a server.
- A DuckLake catalog can itself be served over Quack (`ATTACH
  'ducklake:quack:localhost'`, experimental, with a `TYPE quack` secret).
  That removes the one-process limit of a DuckDB-file catalog without
  running PostgreSQL, which fits the self-hosted scope. A `backend =
  "quack"` for `attach_ducklake()` is a candidate, marked experimental.

### Bug found on the way

`plot_snapshots()` files compaction snapshots under "other". Its classifier
(`classify_change_tokens()`, `R/plot_snapshots.R:421`) looks for
`flushed_inlined` and `compacted`, but DuckLake writes `merge_adjacent` and
`rewrite_delete` (in 1.0 as well; the extension source has the same keys on
both branches), and 1.1 adds `compacted_table` for catalogs written by older
versions. View and macro keys (`views_created`, `scalar_macros_created`, and
so on) also fall through to "other". The test uses a made-up `compacted`
token, which is why it passes.

## Nested schemas (#72)

The probes show where the package stands. `create_schema("sales.europe")`
makes one top-level schema whose name contains a dot. Reads and writes
through `"sales.emea.cars"` happen to work, because `quote_ident()` quotes
each part and 2.0's binder resolves the first part as a schema when no
catalog has that name. The metadata lookups do not: `split_table_name()`
keeps the last two parts, so `list_ducklake_tables()` and
`get_table_comments()` report the schema as `emea`, and lookups keyed on
`schema_name` (the list in #72) match any schema with that last component.

`duckdb_tables()` and `information_schema.tables` give only the last
component as well. `duckdb_schemas()` has `parent_schema` and
`parent_schema_oid`, and `duckdb_tables()` has `schema_oid`, so full paths
can be rebuilt from the catalog functions; in the metadata tables
`ducklake_schema` has a new `parent_schema_id`. Snapshot change entries
record the full quoted path (`created_table:"sales"."europe"."orders"`).

My recommendation is to treat every dot in a table name as a path separator
and resolve names inside one lake: `"sales.europe.orders"` is table `orders`
in schema `sales.europe` of the current lake (or `ducklake_name`), and
`schema_name` arguments take the same dotted path. `create_schema()` would
create missing parents, as `mkdir -p` does. Two consequences:

- A schema whose name contains a dot is no longer reachable through the
  package. That seems acceptable.
- A leading lake name (`"lake.sales.cars"`) becomes ambiguous. The package
  could strip a first component equal to the lake's name, which is
  deterministic, or refuse it. Only one test uses a three-part name, and it
  is about parsing SQL (`bare_table_name()`), not a user call.

The other route, resolving the first part against attached catalogs the way
DuckDB's binder does, inherits the ambiguity DuckLake's own docs warn about
("keep schema names distinct from other attached catalog names").

This is the largest change in the pass. It touches `split_table_name()`,
`resolve_table_ref()`, `table_filter()`, `table_ids_for_name()`,
`schema_exists()`, `pending_keys_key()`, the option `scope_entry` matching,
the change-map targets, `schema_history()`, and every listing function,
which together are most of the package's internals. It also bears on
WilDoane's `make_layer()` proposal in #81, since nested schemas make
`bronze.labs` and `silver.labs` natural.

## Proposed PRs, in order

1. Baseline: `duckdb (>= 2.0.0)`, `dbplyr (>= 2.6.0)`; remove the
   1.5.2 and 1.5.3 version gates and the missing-function fallback; fix the
   seven failing tests; abort early on future timestamps; fix the
   `plot_snapshots()` classifier and the compaction messages; run CI on
   duckdb 2.0 (from r-universe until CRAN has it).
2. Catalog versions and the storage hazard: `ducklake_version`,
   rewritten `automatic_migration` and `metadata_schema` docs, the format
   version in `get_ducklake_info()`, optionally `migrate_ducklake()`, and
   the DuckDB-file warning in NEWS, `attach_ducklake()`, and the deployment
   article.
3. Layout and options in DDL: `create_table(partition_by, sort_by,
   options)`; table options carried inside the rewrite transaction in
   `replace_table()` and `restore_table_version()`;
   `set_ducklake_option()` through `ALTER TABLE ... SET` for tables, plus a
   way to reset. With options no longer forcing a second snapshot,
   `restore_table_version()` could also run inside a caller's transaction
   instead of refusing.
4. Nested schemas (#72): as above, with tests on DuckDB and SQLite
   catalogs.
5. Smaller 1.1 features: epoch transforms; the two new compaction
   arguments; `set_column_default()`; typed literals in
   `render_sql_literal()`; column comments carried by `create_view()`;
   `skip_stats_columns` and the new `auto_compact` rule in the options and
   maintenance docs; the `"NULL"` type in the docs.
6. Quack: stable wording, the new server and client options, and the
   experimental DuckLake-over-Quack backend if wanted.
7. Docs and release: README and articles move from DuckLake 1.0 and
   DuckDB 1.5 to 1.1 and 2.0; `.claude/CLAUDE.md` gets the corrections
   listed below; ducklake 1.0.0 goes to CRAN once duckdb 2.0.0 is there.

PRs 1 and 2 are small. PR 3 removes more code than it adds. PR 4 needs its
own design review.

## Decisions for Travis

1. Floor: require duckdb 2.0.0 (recommended), or support 1.5.x and 2.0
   side by side.
2. Nested-schema names: every dot is a path inside one lake (recommended),
   or resolve the first part against attached catalogs. If the former,
   strip or refuse a leading lake name.
3. Untyped `NULL` columns: document (recommended), warn, or cast.
4. Future timestamps: abort with a clear message (recommended), or clamp to
   now.
5. Quack-served DuckLake catalogs: an experimental `backend = "quack"` now,
   or docs only.
6. `restore_table_version()` inside a transaction: allow it once PR 3
   lands, or keep the refusal.

## How the probes ran

Each finding above comes from a short SQL sequence against a fresh lake.
The scripts are in this session's scratchpad (not kept). The ones worth
turning into tests, because the package depends on the result:

- Options in the rewrite transaction: `BEGIN; DROP TABLE t; CREATE TABLE t
  AS ... LIMIT 0; ALTER TABLE t SET PARTITIONED BY (grp); ALTER TABLE t SET
  SORTED BY (id DESC); ALTER TABLE t SET (parquet_compression = 'zstd',
  target_file_size = '128MB'); INSERT INTO t ...; COMMIT;` gives one
  snapshot with both options stored.
- `set_option()` on a transaction-local table: refused.
- `ALTER TABLE ... SET (...)` after an inlined insert in the same
  transaction: accepted.
- `CREATE OR REPLACE VIEW` after `COMMENT ON VIEW` and `COMMENT ON COLUMN`:
  both comments gone.
- `MERGE` with two actions, `MERGE ... RETURNING`, `INSERT ... RETURNING`,
  `CREATE TRIGGER`, and `CHECK` on lake tables: all refused.
- Storage: a 1.5.5-made DuckDB-file lake written by 2.0 cannot be opened on
  1.5.5; a SQLite-catalog lake in the same sequence can.

## Release checklist for 1.0.0 (added 2026-10-22)

The six implementation PRs (#82 through #87) and this docs sweep are open
as a stack. The release waits on duckdb 2.0.0 reaching CRAN, since
DESCRIPTION requires it.

1. Merge the stack in order, each parent without deleting its branch,
   retarget the child to main, then delete (the children get CI runs only
   once retargeted).
2. When CRAN has duckdb 2.0.0: drop the `extra-repositories` lines from
   the three workflows, and confirm CI is green from CRAN alone.
3. Re-render `README.md` with `devtools::build_readme()` against the
   installed 1.0.0 candidate (dplyneage, webshot2, and Chrome needed), so
   the printed results come from the 2.0 code; the 0.9.0-era output is
   still in place.
4. Release PR: `Version: 1.0.0` in DESCRIPTION, `# ducklake 1.0.0` as the
   NEWS heading, `cran-comments.md` finalized (the draft is in the repo;
   confirm its results line against the check at 1.0.0), `R CMD check
   --as-cran` with and without the extension.
5. Submit; annotated tag on the merge commit; GitHub release from NEWS;
   dev-version PR (1.0.0.9000).
6. Watch upstream: duckdb/duckdb#27663 (COMMENT ON qualifiers),
   duckdb/duckdb#27269 (CONNECT under a client that prepares), and
   DuckDB 2.0.1 (due November), which may change either.
